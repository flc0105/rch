# Remote Control Hub

A lightweight remote control and operations platform for managing connected Python and Go clients through a web UI.

It combines an interactive shell, remote file operations, script execution, background jobs, artifact collection, agent building, and session-based web access control in a single project.

> **Important**
> Use this project only in environments you own or are explicitly authorized to manage. The repository includes powerful remote execution and persistence-related utilities and should be treated as an administrative/automation tool for controlled use.

## Overview

Remote Control Hub is a server/client project for operating remote endpoints from a browser-based control panel.

At a high level, it provides:

- A **web console** for shell-like command execution and live output streaming
- A **server CLI** path that can use the same core session/command infrastructure without the browser
- A **device list** with online/offline status
- A **remote file browser** with common file operations
- **Artifacts** for previews and downloads
- **Scripts** for one-shot actions organized by directory
- **Background jobs** for long-running or repeated monitoring tasks
- **Process/app inspection** and kill operations
- **Command history** and execution history views
- **Agent builders** for multiple delivery modes
- A simple **session-based auth layer** plus static API token support

The Server stores structured runtime state in its embedded SQLite database (`runtime/rch.db`). Artifact contents, resource source files, and selected configuration files remain filesystem-backed.

The project provides a local Server console and Web UI, plus a standalone remote CLI (see [RCH CLI](docs/rch_cli.md)).

- `rchserver.py` starts the socket server and interactive CLI loop
- `run_web.py` starts the same server core plus the Flask web app

The main execution and transport components are:

- **Command/control messages** use a custom socket protocol
- **File payload transfer** uses HTTP or independent TCP data sockets for managed transfers
- **Heartbeat/RTT** are first-class connection metrics and are exposed to the UI and server built-ins
- **Watchdog support** is split into a remote control watchdog and a local self-healing watchdog
- The project supports both lightweight **shell-like commands** and structured **`acmd` commands**

## Protocol and Execution Model

### Command and file transport

The socket layer uses JSON messages over a length-prefixed framing protocol (`RCHSocket`). Commands, structured Control requests, results, cancellation, and heartbeats use the main session. Managed file transfer uses HTTP or a separate TCP data socket according to the Python Client transfer mode. Browser HTTP requests and WebSocket events remain separate from the Client session. See [Socket Protocol](docs/socket_protocol.md) and [File Transfer](docs/file_transfer.md).

### Client handshake

After the TCP or TLS/TCP connection is established, the client sends an initial `info` handshake payload.

The handshake reports runtime details including:

- client ID
- platform / OS version / hostname
- integrity level
- current working directory
- command manifest
- system paths
- Python version
- process ID / process name / username
- launch command
- current file transfer mode
- current Python execution mode
- Remote Control Watchdog / Local Heartbeat Watchdog enabled flags
- client build version

The Server exposes these execution characteristics in the UI and CLI.

### Heartbeat and RTT

The server periodically sends a `heartbeat` message to each session. The client responds with `heartbeat_ack`, echoing the heartbeat ID and server timestamp while also attaching client-side timing/context fields.

The server uses that round-trip acknowledgement to maintain:

- `last_seen_at`
- `last_heartbeat_sent_at`
- `last_heartbeat_ack_at`
- `last_rtt_ms`

RTT is computed from the heartbeat exchange and exposed in the UI and through the Server `rtt` built-in.

### Watchdog model

Watchdog behavior includes Remote Control, Local Heartbeat, and Process Recovery responsibilities. See [Watchdog](docs/watchdog.md) and [Process Recovery](docs/process_recovery_watchdog.md).

#### Remote Control Watchdog

The **Remote Control Watchdog** is for **out-of-band remote control**.

It runs in the shared watchdog worker and polls a dedicated HTTP endpoint:

- server side queues control actions per client
- client watchdog polls independently of the main socket command stream
- supported remote control actions are `kill`, `relaunch`, and `clone`

The independent channel remains available when the main command channel is busy or blocked, provided the watchdog and HTTP endpoint are reachable.

The independent HTTP control path is described in [Watchdog](docs/watchdog.md). Device menu actions follow the connection direction and the normal session lifecycle.

#### Local Heartbeat Watchdog

The **Local Heartbeat Watchdog** is for **local self-healing / parent liveness monitoring**.

The main client process periodically feeds heartbeat state to a local heartbeat file, and the watchdog worker monitors that file. If the local heartbeat is stale beyond the configured timeout, the watchdog can restart the parent client process.

In short:

- **Remote Control Watchdog** = independent remote control channel (`kill` / `relaunch` / `clone`)
- **Local Heartbeat Watchdog** = local crash/hang recovery for the client process itself

The `watchdog` command shows a flat key/value runtime status by default; `watchdog --json` returns the same flat dictionary as JSON.

### Shell-like commands vs `acmd`

The project supports **two command styles**.

#### 1. Shell-like commands

Shell-like commands are lightweight and intentionally simple:

- command name is the first token
- the remaining text is treated as a single raw argument string
- if the command name maps to an exported client method, that method is invoked
- otherwise execution falls back to the generic `shell(...)` handler

This is the familiar path for commands such as:

- `cd ...`
- `shell_bg ...`
- `shell_stream ...`
- `pyexec ...`
- `pyexec_stream ...`
- many file/process/platform helpers

This path is reflection-driven: exported client command methods are discovered from the command object and surfaced through the client manifest.

#### 2. Structured `acmd`

`acmd` is the structured command path:

```text
acmd <command> [--key value] [--key=value] [--flag] [-- positional...]
```

An explicit **command registry** and option specification define this path.

It is useful when a command needs:

- clearer argument schemas
- typed options
- validation
- positional + named option mixing
- better manifest/help generation

### Structured operations

Remote Files, Scripts, Jobs and other structured operations use typed Control requests. The command line and Web forms share the corresponding validation and execution entrypoints. See [Socket Protocol](docs/socket_protocol.md).

### Command context, timeout, and cancellation

Each command execution gets a command context that can carry:

- timeout
- cancel event
- cleanup hooks
- cancel policy metadata

Timeout and cancellation are tracked per execution.

**Ordinary shell-like command execution policy (Client):**

- `@timeout(seconds)` records a command-local **default execution budget**. This is metadata only. A `timeout` or `_timeout` explicitly supplied in the Server's command-message `extra` is an execution limit, and the Client applies the **shorter** of the two limits. Neither limit forcibly interrupts arbitrary in-process Python code; execution must reach a checkpoint or managed I/O.
- `@cancel_policy(mode)` is metadata with exactly three modes: `none` (not cancellable), `cooperative` (checks cancellation at checkpoints or interruptible I/O), and `process` (execution owns a managed subprocess and can terminate it). **`shell` and `shell_stream` use `process`**. The default for otherwise unannotated ordinary commands is `none`. Strategy-dependent HTTP transfer and Python execution policy is selected at runtime; `subprocess_pipe` uses `process`, `inproc` uses `none`.
- `@confirm` defines an independent confirmation policy. `relaunch_instance` requires confirmation; `kill_instance` executes without a confirmation prompt.
- Execution checks cancellation and timeout at invocation and at cooperative checkpoints or managed I/O. Arbitrary in-process Python loops cannot be forcibly interrupted.
- Cancellation states are distinct: the Server records `requested` on sending a request; Client `cancel_ack` says `accepted` only when the operation allows cancellation; Client reports a terminal `stopped` only after actually observing cancellation **and returning**. A command that ignores cancellation but completes normally reports `completed`, not `stopped`.
- Repeated requests preserve an existing `accepted`, `stopped` or `completed` acknowledgement.


### Python execution strategy

Python code execution supports two runtime strategies:

- **`inproc`** — executes inside the current interpreter with `exec()`
- **`subprocess_pipe`** — starts a child Python process and communicates through stdin/stdout pipes

Trade-offs:

- `inproc` is lightweight and direct, but cancellation/isolation are limited
- `subprocess_pipe` is heavier, but gives better cancellation/timeout/process control behavior

Runtime configuration selects the active default mode (`SCRIPT_DEFAULT_EXECUTION_MODE`), and the client handshake reports that mode back to the server.

### Python collect vs stream, and script execution semantics

`pyexec` collects output; `pyexec_stream` streams output. Script execution supports both `collect` and `stream`, independently of the supported Python execution strategy. Script metadata, explicit runtime selections and Client defaults determine the actual modes. See [Scripts](docs/scripts.md).

### File transfer modes

Python Client supports `http_simple`, `http_streaming` (default), and `tcp_streaming`. Managed transfers snapshot the selected mode at task start. TCP streaming uses a separate data socket on the Bind TCP or Reverse TCP/TLS listener, with progress and cancellation through the Transfer lifecycle. Browser-to-Server uploads and Artifact downloads use HTTP. Ordinary command, Script and Job HTTP operations use HTTP streaming when `tcp_streaming` is selected. Go Client uses HTTP file transfer.

## Jobs and Scripts

### Background jobs

Background jobs are long-running tasks managed by the server/client job framework.

Job features:

- job catalog APIs
- metadata-driven parameter forms
- start / stop controls
- report ingestion
- support for platform tags and parameter schemas
- file/artifact association so job outputs remain queryable later

Typical use cases:

- monitoring application launches
- clipboard monitoring
- screenshot or scheduled capture flows

### Scripts

Scripts are one-shot utilities stored under `server/resources/scripts/`.

Script features:

- directory-based organization
- metadata via `SCRIPT_METADATA`
- script library UI with folder navigation
- edit/upload/delete support
- structured execution via `/api/connections/<client_id>/scripts/run`
- terminal execution through `script exec <name>`
- parameter normalization before execution when metadata declares params
- Script, Job, and External Tool runtime parameters share one canonical schema/coercion core
- shared parameter types include `string`, `password`, `textarea`, `integer`, `number`, `boolean`, `select`, remote path pickers and `path_list`
- `label` falls back to `name`, and `select` uses `options` consistently across all three surfaces
- multi-path parameters (`remote_files` / `remote_folders`) use structured arrays such as `["/a", "/b"]`

This makes scripts well-suited for:

- small data collection tasks
- platform-specific admin actions
- quick UI prompts or persistence helpers
- repeatable one-off actions that do not need a full job lifecycle

### History, quick history, and execution history

Command History separates **Quick History**, **Activity Center**, and independently persisted Pinned Commands.

#### Quick history

Quick history is designed for fast reuse:

- de-duplicated by command text
- keeps the latest entry per command
- supports pin/unpin
- supports moving pinned items up/down
- is optimized for reuse from the terminal

Replay helpers include:

- `history run <index>`
- `!<index>` as shorthand syntax

#### Execution history

Activity Center preserves the operation record, subject to configured output retention limits:

- no de-duplication
- full command status
- start/end working directory details
- output records and structured operation results
- lifecycle timestamps (`created_at` / `started_at` / `updated_at` / `finished_at`), with duration derived when displayed
- associated file/artifact references

Activity Center is the execution trace; Quick History is the recent-command reuse view. See [Command History](docs/command_history.md).

### History/job file association

History and background job records can retain related file references, so later inspection can answer questions such as:

- what files were produced by this command?
- what screenshot/archive/log belongs to this background job?
- is the original artifact still downloadable/previewable?

That linkage is one of the reasons the server records upload metadata like source type, command ID, and related path.

### Alias support

The server supports persistent aliases with simple placeholder substitution.

Characteristics:

- aliases are stored persistently in JSON
- supports platform groups: `common`, `win`, `mac`, `linux`, and `ios`
- effective alias lookup applies the relevant platform overlay
- placeholder names are the parameter identity; repeated placeholders such as `<path> ... <path>` reuse the same value
- positional invocation follows each unique parameter name in first-appearance order
- terminal invocation also supports named arguments as `--name value` or `--name=value`; named keys must match `[A-Za-z_][A-Za-z0-9_-]*`
- use a leading `--` to force positional mode when the first positional value itself starts with `--`

Examples:

```text
alias set ll = shell ls -la
alias set --platform win desk = cd <path>
alias unset ll
```

Both named and positional invocation resolve through the same placeholder binding rules.

## Agent Build Modes

The Agent Builder coordinates dispatch and output management. **Python Bundle** (`python`) packages Python source files and requires Python on the target machine. Go Loader (`go_loader`) independently builds an executable that requests a Python Bundle (`python`) from the Server at runtime.

Each build request selects a registered builder. The Agent Builder UI displays the available modes; builders share source staging and configuration injection.

Both Go build modes share cross-compilation and subprocess management, including build logs, timeouts and error reporting.

### Python Bundle

- Packages `client/`, `core/`, and `rchclient.py` into a zip archive
- Injects build version into the bundle configuration
- Designed for source-based delivery/update flows
- Used by the Python-client `update` workflow to fetch and launch a newer bundle automatically

### Go

The Go builder is a lightweight standalone client option for use cases where a smaller executable is preferred.

Go can target a TCP listener or TLS/TCP listener. TLS builds embed the
selected listener certificate SHA-256 fingerprint, verified by the Go Client before
sending its RCH handshake. Builds with no TLS listener selection use TCP.

The standalone Go Client supports:

- unified heartbeat/message protocol participation
- basic shell execution
- `cd` / `pwd`-style command support
- `getinfo`-style environment reporting
- Remote Files directory listing, pagination, searching, Quick Jump system paths,
  directory creation, rename/delete, and file/directory copy or move; the existing
  Server Remote Files API uses the same structured command contract as Python

Go also supports HTTP file transfer, ZIP operations, preview and limited text editing through Remote Files. Script Library execution uses a locally available Python interpreter with collected or streamed output; the Python Client SDK is not injected into that interpreter. Background Jobs, Clipboard, PTY, Screen View and watchdog features remain Python Client capabilities, subject to platform support. See [Remote Files](docs/remote_files.md) and [Scripts](docs/scripts.md).

### Go (Loader)

The Go Loader prepares and launches a Python Bundle. Responsibilities include:

- collecting local environment basics such as OS/arch/host/IPs
- reporting to the server via HTTP
- detecting Python availability and reporting the result
- resolving a working directory under the user home directory
- requesting a fresh bundle build from the server
- downloading and extracting the bundle
- launching `rchclient.py` via `python3` / `python`
- reporting launch details (paths, PID, build version)
- exiting after handoff

Loader reports are stored as JSON Lines under the Server runtime logs.

## Authentication

The web app includes a session and token-based authentication layer for authorized administration.

### Supported auth methods

- **Session login** for the browser UI
- **Static API token** for external API clients

### Authentication behavior

- administrator username, password hash, API Token, and Session Secret are stored in `SERVER_RUNTIME_DIR/auth.json`
- no registration flow; administrator credentials are stored separately from the SQLite runtime database
- session cookie based login for the web app
- the account menu shows the current administrator username, supports password changes, and exposes the administrator API Token in Authorization Info for copying
- password changes atomically update `auth.json`, reload the active password credential, and sign out the current browser session
- browser password submissions use the lightweight masked payload format
- API token accepted via auth guard

### Relevant config entries

- `RCH_SERVER_RUNTIME_DIR`
- `RCH_WEB_AUTH_SESSION_DAYS`
- `RCH_WEB_SESSION_COOKIE_NAME`

## Runtime Data

The Server stores structured runtime state in the shared SQLite database `runtime/rch.db`, while file-oriented artifacts and configuration remain on the filesystem.

Examples include:

- artifacts
- command history
- execution history details
- pinned paths / quick jumps
- web files / previews
- agent build outputs
- loader logs
- recent devices cache

### Saved Bind connection targets

Bind endpoints are stored in `runtime/rch.db` as individual `saved_bind_targets` rows. The Device Bar keeps each Host/Port target available for manual reconnection after its Client disconnects; Reverse uses machine-based offline history. The table is initialized by `RchDatabase`. See [RCH Database](docs/rch_database.md) for schema validation and backup behavior.

### Recent devices cache

Recent-device state is stored in `runtime/rch.db` (`recent_devices`).

Behavior:

- one record per `machine_id`
- online device updates refresh the current machine snapshot
- offline devices remain available as recent entries
- machine aliases, stable ordering, and hidden machine/client state are persisted with the recent-device record

`RchDatabase` centrally initializes all 21 SQLite tables and their indexes, manages thread-local connections and provides shared query helpers, read snapshots and nested write transactions. Service code coordinates business operations; Stores own SQL and persistence mappings. Artifact contents and selected runtime configuration remain filesystem-backed. See [RCH Database](docs/rch_database.md).

### Execution model notes

Execution characteristics:

- command cancellation support depends on the command/strategy being used
- HTTP transfer cancel support depends on whether transfer mode is `http_simple` or a streaming mode
- Python execution semantics differ between `inproc` and `subprocess_pipe`
- Python commands and Script Library execution support collected or streamed output
- server built-ins, aliases, client manifests, and history shortcuts all participate in the final terminal UX together

## Operational boundaries

- Each Client has one active foreground execution slot for commands and Scripts. Additional foreground requests receive a busy response. Managed Transfers, Remote Files Control requests, PTY and Monitor channels have separate execution paths.
- Python Bundle provides the broader Client feature set; Go provides the standalone executable feature set described in [Agent Build Modes](#agent-build-modes).
- Most operational APIs target a connected Client. For local machine operations, run a Client on the Server host.
- Command outputs include text, structured JSON, WebSocket events and Artifact references. Consult the specific command or API contract when integrating automation.
- Features with optional Python dependencies import them on demand. Install the required packages for the target platform before using dependency-backed operations.

## Client execution commands

The Client command manifest contains the common execution primitives.

### Core execution primitives

```text
cd
shell
shell_bg
run_bg
shell_stream
pyexec
pyexec_stream
```

Their roles are intentionally different:

| Command | Behavior |
| --- | --- |
| `cd <path>` | Changes the Client process working directory; without an argument, reports current CWD |
| `shell <command>` | Runs a shell command and waits for the final result |
| `shell_bg <command>` | Starts a background process and returns immediately with the PID |
| `run_bg <program> [args...]` | Starts the executable directly in an independent background session and returns its PID; no shell is involved |
| `shell_stream <command>` | Runs a subprocess while streaming output live to the terminal |
| `pyexec <code>` | Executes Python and returns collected output |
| `pyexec_stream <code>` | Executes Python with streaming output |

Windows additionally exposes:

```text
run <command>
```

which starts a program detached without waiting.

Normal shell syntax is passed through to the target shell, so regular shell redirection can be used where the target shell supports it. If the Python Client working directory disappears, it attempts to recover to Home or the system temporary directory at execution boundaries; CWD reporting failures alone do not disconnect the session.

### Python execution modes

Python execution has two runtime strategies:

```text
inproc
subprocess_pipe
```

The active strategy is controlled by:

```text
SCRIPT_DEFAULT_EXECUTION_MODE
```

and is exposed through Client Runtime Configuration.

`subprocess_pipe` isolates the Python command in a subprocess while preserving collected/streamed output behavior.

### Session lifecycle commands

```text
kill_instance
relaunch_instance
reexec_instance
spawn_instance
```

- `kill_instance` terminates the current Client session/process.
- `relaunch_instance` starts a fresh Client process and reconnects.
- `reexec_instance` replaces the current process image.
- `spawn_instance` launches an additional Client instance without terminating the current one.

Multiple Client instances can share one `machine_id`. Bind does not support spawning or relaunching an additional instance on the fixed listener; see [Connection Lifecycle](docs/connection_lifecycle.md).

### Runtime/session maintenance commands

```text
watchdog
update
clean
set
help
```

- `watchdog` displays the flat guard/watchdog runtime status; use `watchdog --json` for flat JSON.
- `update` builds/downloads/extracts/starts the newest bundle.
- `update --keep-old` keeps the old ordinary Reverse Client after the new Client registers with Server.
- `clean` previews selectable Client residue and obsolete Release cleanup; `clean --no-confirm` runs without Interaction Broker.
- `set` reads/writes Client runtime configuration overrides.
- `help` is generated from the actual exported command manifest.

## Safe Client update handoff

`update` builds, verifies (SHA-256), and publishes an immutable Python Source Bundle. On macOS, Linux and Windows, ordinary Reverse Clients start the candidate while the old process remains online; the old process exits after the candidate receives a Server Session Token and passes the PID/Revision/liveness check. `update --keep-old` retains the old ordinary Reverse process.

Ordinary Bind Clients send the preparation result to Server, then end the old session and process after the command finishes. A short-lived local handoff starts the replacement only after the old listener is released. Readiness is acknowledged after `listen()` succeeds; operators reconnect manually from Server. Candidate and rollback startup output is saved in the handoff log, and rollback is only reported successful after the previous Client listens again. macOS launchd jobs use a stable Launcher entry and a job-specific Release pointer, preserving service ownership and other plist settings. iOS/Pythonista installs the Release and presents its entry path for manual startup. systemd and Windows-managed service updates require manual service handoff.

The Update readiness channel is local and authenticated.

## Agent build, Bootstrap, and outputs

The Agent workflow includes three builder modes and supporting build and output management features.

Supporting features include:

- Agent Builder dialog
- Agent Outputs dialog

- build status
- target platform/arch
- downloadable build artifacts
- build complete/error WebSocket events
- bootstrap Python script
- bootstrap PowerShell script
- build/version injection

- temporary bootstrap-file cleanup

Source revision checks run independently of bundle construction.

### Bootstrap runtime and release layout

Python Bootstrap, Windows PowerShell Bootstrap, and the standalone Go Loader request an explicit `python` build and consume its `sha256` value from `/api/agent/build`. The downloaded ZIP is checksum-checked, safely extracted to a staging directory, and installed afresh for each run. All use the following layout under the target user's home directory:

```text
~/client_bundle/
├── runtimes/python-embed/
├── downloads/
└── releases/<build_version>/
```

Agent output filenames use the `rchclient` prefix and builder kind. For Python Bundles, `build_version` is the ZIP filename stem. Bootstrap, Go Loader and Client Update install under that release folder name, preserving existing releases.

The Client source requires **Python 3.10 or newer**. On Windows the bootstrap prefers an existing suitable embedded runtime, then suitable local Python; if neither is available it requests the Windows Embed archive using the detected platform/architecture. The published `python-embed` package supports Windows amd64 (Python 3.13.13; Windows 7 is unsupported). macOS uses local Python. Launching the Client is detached (Windows also hides its window). Bootstrap initialization uses the Web port.

Both generated Python and Windows PowerShell bootstraps print each stage to the console: runtime source (cached Embed, local Python, or Embed download), build request/version, Bundle download and checksum, extraction/replacement directory, and detached launch. Python Client `update` uses the same Release root and downloads temporary ZIPs under `~/client_bundle/downloads/` (sibling of `releases/`), validating SHA-256 before publishing. The Bundle ZIP residue cleanup also targets that downloads directory without touching cached Python Embed packages.
